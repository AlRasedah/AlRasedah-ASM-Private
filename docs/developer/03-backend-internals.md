# 3. Backend internals

## 3.1 Request lifecycle

```text
HTTP request
  └─ RequestContextMiddleware (app/main.py)
       • request id (X-Request-ID, sanitized or generated) → RequestContext + log context
       • client IP from request.client (uvicorn/gunicorn proxy headers set it behind nginx)
       • API rate limit per bearer-token suffix or IP (ASM_API_RATE_LIMIT_PER_MINUTE)
  └─ router → endpoint dependencies
       • require(Permission.X)  → get_principal()  (app/api/deps.py)
            – Bearer "asmpat_…" → API token (system session lookup)
            – otherwise JWT → session row checked (not revoked/expired) → user active
              → membership re-read so the role is always current
            – fills RequestContext.user_id / actor / tenant_id (used by audit)
       • get_db() → new_session(tenant_id, user_id)  — RLS-scoped session
         or get_system_db() for auth/platform endpoints
  └─ endpoint: validate (pydantic) → call service → db.commit() → return schema
  └─ exception handlers: AppError → {"error": {...}} with its status; validation → 422;
     anything else → logged, generic 500 (no internals leaked)
  └─ middleware adds security headers + CSP (strict for API, relaxed only for /api/docs)
```

Conventions:

- Endpoints are **sync `def`** functions (FastAPI runs them in a threadpool). The whole
  backend uses **synchronous SQLAlchemy** so the same service code runs in the API and in
  Celery workers. Only the sensor framework is async (subprocess management).
- **Endpoints commit explicitly.** Services `flush()` but do not commit, so an endpoint can
  compose several service calls in one transaction. The `get_db` dependency rolls back on
  exceptions and always closes the session.
- Services raise `AppError` subclasses; never `HTTPException`.
- Every mutation a human performs calls `audit.record(...)` in the same transaction.

## 3.2 Sessions and Row-Level Security

`app/db/session.py` registers one SQLAlchemy event listener:

```python
@event.listens_for(Session, "after_begin")
def _apply_rls_context(session, transaction, connection):
    connection.execute(text("SELECT set_config('app.tenant_id', :t, true), "
                            "set_config('app.user_id', :u, true), set_config('app.bypass_rls', :b, true)"), ...)
```

It runs at the start of **every** transaction (including the new transaction that begins
after a `commit()`), reading the context from `session.info`. The third argument `true`
makes the setting transaction-local, so pooled connections never leak context.

Session constructors:

| Function | Context | Use |
|---|---|---|
| `new_session(tenant_id, user_id=None)` | tenant | everything tenant-owned |
| `new_session()` | none | sees **no** tenant rows (fail closed) |
| `system_session()` | `bypass_rls=on` | authentication lookups, platform admin, schedulers, cross-tenant loops |
| `session_scope(...)` | context manager that commits/rolls back | scripts |

Policies (generated by `app/db/rls.py`, installed by migration 0001):

```sql
ALTER TABLE assets ENABLE ROW LEVEL SECURITY;
ALTER TABLE assets FORCE ROW LEVEL SECURITY;          -- applies to the table owner too
CREATE POLICY tenant_isolation ON assets
  USING      (current_setting('app.bypass_rls', true) = 'on'
              OR tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid)
  WITH CHECK (same);
```

Special cases: `scan_profiles` (rows with `tenant_id IS NULL` are readable by everyone,
writable only with bypass), `users` (visible if it is you or a member of the current
tenant), `tenants` (only your own row), `audit_logs` (select/insert only; a trigger blocks
UPDATE/DELETE/TRUNCATE even with bypass), `user_sessions`/`password_reset_tokens`
(system sessions only).

Why FORCE + non-superuser role: table owners and superusers bypass RLS by default. The app
role owns the tables (so migrations work) but FORCE applies the policies to it; it is not a
superuser and has `NOBYPASSRLS` (`scripts/dev_db.py`, `docker/postgres/init/01-app-role.sh`,
asserted in `tests/backend/conftest.py`).

**Pattern for background work:** find the tenant with a system session, then do the work in
a tenant session. Example from `app/workers/tasks.py`:

```python
tid = _scan_tenant(scan_id)            # system session, one query
with new_session(tid) as db:           # everything else under RLS
    ...
```

Pitfall (a real bug found while writing this handbook): a query meant to span tenants
must not run in a tenant session — RLS silently narrows it. `orchestrator.try_start`
counted "all running scans" in the tenant session, so the global concurrency cap only saw
one tenant; it now takes that count from a short-lived system session.

## 3.3 Authentication (`app/auth/service.py`, `app/api/v1/auth.py`)

**Login** (`authenticate`): normalize email → look up user (system session) → if missing,
verify against a dummy hash (timing equalization) → lockout check → Argon2id verify
(failures increment `failed_login_count`; at `ASM_ACCOUNT_LOCKOUT_THRESHOLD` the account is
locked for `ASM_ACCOUNT_LOCKOUT_MINUTES`) → rehash if parameters changed → pick the tenant
(`resolve_tenant`: requested → default tenant → first active membership; platform admins
may have none) → if MFA enabled return a 5-minute MFA challenge JWT, otherwise
`_issue_session`. Every outcome is audited. The router also rate-limits per IP and per email.

**Session tokens**:

- Access token: HS256 JWT, 15 minutes, claims `sub`, `tid`, `role`, `sid` (session id), `pa`
  (platform admin), audience `asm-api`. The SPA keeps it in memory only.
- Refresh token: 32 random bytes, stored as HMAC-SHA256 (`hash_token`) in `user_sessions`,
  sent as cookie `asm_refresh` (`HttpOnly; SameSite=Strict; Path=/api/v1/auth`).
- CSRF: cookie `asm_csrf` (readable by JS) must be echoed in `X-CSRF-Token` on `/auth/refresh`.
- **Rotation**: each refresh replaces the token and keeps the previous hash in
  `previous_token_hash`. Presenting a *previous* token again means it was stolen: the
  session is revoked and `auth.refresh_token_reuse` is audited.
- Sessions have a sliding expiry (`ASM_REFRESH_TOKEN_TTL_DAYS`) capped by an absolute
  lifetime (`ASM_SESSION_ABSOLUTE_TTL_DAYS`).
- `get_principal` checks the session row on **every request**, so logout, password change,
  role change and deactivation take effect immediately (not after token expiry).

**MFA**: TOTP (pyotp). The secret is encrypted with `core.crypto` (AAD `user:<id>:mfa`).
Setup → enable with a valid code → login requires `/auth/mfa/verify`.

**Password reset**: single-use random token stored hashed with a 30-minute expiry; the
forgot endpoint answers identically whether or not the account exists; reset revokes all
sessions. Invitations reuse the same token table with a 3-day expiry; when SMTP is not
configured the one-time link is returned to the administrator instead of being emailed.

**API tokens**: `asmpat_` + random, stored hashed; bound to one tenant; role capped at the
owner's current role on every request; cannot create further tokens.

**Email addresses** are validated permissively (`schemas/common.Email`: `x@y`, lower-cased).
Strict validators reject reserved domains like `.local`/`.internal`, which enterprise
directories use (this broke the demo login before it was changed).

## 3.4 Authorization (RBAC)

`app/auth/permissions.py` defines ~26 permissions (`assets:read`, `scope:write`,
`findings:accept_risk`, `tenants:admin`, …) and maps roles to sets:
viewer ⊂ security_analyst ⊂ tenant_admin ⊂ platform_admin. Endpoints declare
`Depends(require(Permission.X))`. Notable rules: only tenant admins accept risk or change
scope; users can only grant roles ≤ their own (`can_assign`); the last tenant admin cannot
be demoted/removed. Custom roles later = a table mapping role names to permission lists;
endpoint code does not change.

## 3.5 Errors

`app/core/errors.py`: raise `NotFound("...")`, `ValidationFailed("...", details=[...])`, etc.
The handler emits `{"error": {"code": "...", "message": "...", "details": ...}}`. Objects of
other tenants are simply invisible under RLS, so they produce **404**, never 403 — this
avoids leaking existence.

## 3.6 Audit log (`app/services/audit.py`)

`record(db, Action.X, object_type=..., object_id=..., previous=..., new=...)`:

1. takes `pg_advisory_xact_lock(hashtext('audit:<tenant>'))` to serialize the chain;
2. reads the tenant's last hash and `chain_seq`;
3. builds the row with `chain_seq = last + 1` (actor/IP/user agent/request id come from
   `RequestContext`), redacts secret-looking keys, computes
   `sha256(prev_hash + canonical_json(row))`;
4. inserts.

There is one chain per tenant plus a platform chain (`tenant_id` NULL: failed logins for
unknown users, platform actions). **`id` is table-wide** — shared by every chain and
consumed by rolled-back transactions — so a tenant's `id`s always have gaps. People see
**`chain_seq`**, which is 1, 2, 3, … per chain (unique index on `(tenant_id, chain_seq)`,
migration `0002` backfilled older rows).

`check_chain(tenant)` walks the chain in order and fails on the first entry whose
`chain_seq` is not the next number (**sequence gap**), whose `prev_hash` is not the previous
entry's hash (**broken link**), or whose content no longer matches its hash (**edited**). It
returns a `ChainReport` (intact, entries, first bad id/seq, reason); `verify_chain` is the
tuple wrapper used by older callers; the API (`/audit-logs/verify`), UI badge and
`cli verify-audit` all show the reason. Removing entries from the *end* of a chain cannot be
detected from the chain alone — anchor the latest hash externally (SIEM export) if that
matters.

Use `audit.diff(before, after)` to store only changed fields.

## 3.7 Settings

Tenant settings (`tenants.settings` JSONB) and organization settings
(`organizations.settings`) are deep-merged over `DEFAULT_TENANT_SETTINGS` /
`DEFAULT_ORG_SETTINGS` (`app/tenants/settings.py`). Adding a setting = add a default there
and (if user-editable) a field in the `SettingsUpdate` model in `api/v1/settings.py`. No
migration needed.

## 3.8 Secrets and encryption

- `core.crypto.encrypt(plaintext, aad)` → `v1:<key_id>:<base64url(nonce||ciphertext)>`.
  `ASM_ENCRYPTION_KEYS="k2:<new>,k1:<old>"`: first key encrypts, all decrypt.
- `services/secrets.put_secret` stores tenant secrets with AAD `secret:<tenant>:<name>` so
  a ciphertext copied to another row/tenant fails authentication.
- Scanner credentials are decrypted just before dispatch and **sealed** into the
  `SensorJob` with `ASM_SCANNER_TRANSPORT_KEY` (AES-GCM, AAD = job id) so they never sit in
  the broker in clear text.
- The API never returns secret values (only `last_four`, `has_secret`).

## 3.9 Background work from the API

The API never imports Celery tasks. It calls `app/workers/dispatch.py`:

```python
dispatch.start_scan(tenant_id, scan_id)   # Celery: send_task("asm.core.start_scan"); inline: run now
dispatch.recompute_risk(tenant_id, org_id)
dispatch.generate_report(tenant_id, report_id)
dispatch.dispatch_notifications()
dispatch.revoke(task_ids)
```

In `ASM_SENSOR_MODE=inline` these run synchronously in the request (tests and development);
in `celery` mode they enqueue on the `core` queue.

## 3.10 Rate limiting and headers

- nginx: `/api/v1/auth/*` 10 r/min per IP (burst 10), `/api/*` 40 r/s (burst 80).
- App: login/MFA/forgot/reset limits per IP and per account (`core/rate_limit.py`), plus a
  global per-token/IP limit in the middleware.
- Headers: `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`,
  `Permissions-Policy`, COOP/CORP, `Cache-Control: no-store`, CSP, HSTS in production.
